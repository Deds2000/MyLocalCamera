# F3-T05 — `ApprovalDialog` (aprovação de dispositivo)

**Fase:** 3 · **Executor:** agente · **Depende de:** F3-T02, F3-T14b, F3-T14a · **Tempo:** ~3 h · **Contexto estimado:** ~13k tokens

## Objetivo
`ApprovalDialog` totalmente ligado: abre no evento `trust://pending`, **não fecha** com `Esc`/clique fora (equivale a Recusar), foco inicial em **Recusar**, contagem regressiva de 30 s (ao zerar → não aprovado), traz a janela ao primeiro plano + notificação do Windows se estiver minimizada, e segundo pedido simultâneo é ignorado (`busy`, sem diálogos empilhados).

## Leia só isto
Só este cartão + o esqueleto `desktop/src/components/ApprovalDialog.tsx` (F3-T02) + tipos em `desktop/src/lib/tauri.ts`.

## Contexto embutido
`ui/desktop.md` §2.8.1:

```
╭────────────────────────────────────────╮
│  🛡  Permitir que "Pixel 8" se conecte? │
│  Modelo: Pixel 8  ·  IP: 192.168.0.23  │
│  Só aprove se for o seu aparelho.      │
│  ◔ Expira em 27 s                       │
│  [ Recusar ]  [ Só desta vez ] [Permitir sempre] │
╰────────────────────────────────────────╯
```
- Modal (`AlertDialog`); **não** fecha clicando fora nem com `Esc` (equivale a "Recusar" para evitar aprovação acidental).
- Foco inicial em **Recusar**. "Permitir sempre" é o primário (gradiente), mas **não** é o foco inicial.
- Barra/anel de contagem de 30 s; ao zerar, fecha como "não aprovado".
- Janela minimizada → **trazer ao primeiro plano** + notificação do Windows ("Novo aparelho quer se conectar").
- Dois pedidos simultâneos: o segundo é recusado automaticamente (`busy`) — no servidor já acontece (F1-T06); na UI, ignorar o 2º evento enquanto houver diálogo aberto.

`protocol.md` §6.2: `PENDING { timeoutS: 30 }`; aprovado → `WELCOME { accepted:true, sessionId, deviceKey }` (`deviceKey` só em "Permitir sempre"); recusado/sem resposta → `not_approved`; **o token rotaciona ao aprovar**. Textos: `desktop.approval.*` (copy.md) + `common.*`.

**Automação (mandato IA+ADB/harness):** o diálogo roda na WebView2 — o agente opera via UIA (`System.Windows.Automation`): esperar a janela/texto do diálogo, clicar nos botões. O token para o `mock-sender` é lido do `<data_dir>/trust.json` (F3-T13) **sem imprimir**. Se a UIA não chegar fielmente em algum controle, **registrar desvio/bloqueio** (parcial) — nunca pedir clique ao usuário.

**Timer do WebView2 (armadilha da fase):** timers do WebView2 podem ser limitados em janela oculta — a autoridade do timeout é o **Rust** (`lc-server` decide `not_approved` no fim dos 30 s); a contagem da UI é espelho; se a UI zerar, chama `reject` e o servidor confirma; se a janela ficar oculta, o servidor garante o resultado sem depender do timer do JS.

## Passos
1. Slice `trust` (F3-T14a) assina `trust://pending`: se já há pendente → ignorar o evento (FT-3.07).
2. Foco e teclado: ao abrir, `focus()` no botão **Recusar**; `Esc` → `reject()`; clique fora → `reject()`; `Enter` só ativa o botão focado (que é Recusar) — **nada aprova acidentalmente** (UT-3.21).
3. Contagem: 30 s espelhando o `timeoutS` do evento; ao zerar → `reject()` (o servidor também expira; idempotente).
4. Minimizada: ao abrir com a janela minimizada → `win.show(); win.set_focus();` + notificação Windows (plugin; texto por chave i18n). Falha de notificação → log `warn`, sem quebrar.
5. Botões: Recusar → `reject`; Só desta vez → `approve(once)`; Permitir sempre → `approve(always)`. O diálogo fecha quando o evento `session://connection` confirmar (regra da F3-T14a), não na resolve do comando.
6. Shutdown: ao fechar o app com pedido pendente, cancelar (recusado) — o celular recebe `not_approved` (FT-3.10).
