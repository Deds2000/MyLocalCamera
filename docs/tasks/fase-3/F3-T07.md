# F3-T07 — `decode/`: decodificador H.264 (Media Foundation)

**Fase:** 3 · **Executor:** agente · **Depende de:** F3-T13b, F3-T13 · **Tempo:** ~3 h (cartão de risco — ver "Não faça") · **Contexto estimado:** ~14k tokens

## Objetivo
Módulo `decode/` em Rust (dentro de `desktop/src-tauri`): decodificador H.264 via **Media Foundation (MFT)** com aceleração por GPU e **fallback por software** (forçável por variável de ambiente), baixa latência, saída **NV12**, espera o primeiro keyframe, reinicia ao receber SPS/PPS novo, após erro pula até o próximo keyframe e emite `REQUEST_KEYFRAME`, e fila limitada que descarta os quadros mais antigos quando o consumidor atrasa.

## Leia só isto
Só este cartão +, antes de codar: `crates/lc-testkit/src/*` (API de split de Annex-B — o S5 usou `split_access_units`/`is_idr`), `crates/lc-server/src/sessions.rs` + `conn.rs` (como o app recebe os quadros `VIDEO` — **conferir** o canal exposto; se não existir, ver passo 3).

## Contexto embutido
- Vídeo no protocolo (CHEATSHEET/§10): H.264 **Annex-B**, 1 access unit por quadro `VIDEO` (tipo `0x10`); header flags: **bit0 = keyframe**, **bit1 = tem SPS/PPS**; `STREAM_CONFIG { stream, width, height, fps, rotationHint, facing, profile }`; keyframe a cada 1 s; SPS/PPS repetidos em cada keyframe; sem B-frames; `REQUEST_KEYFRAME` = tipo `0x40`, payload vazio (PC→celular).
- Armadilhas da fase: decodificadores de hardware variam entre GPU — **sempre** fallback por software + teste que o force; mudança de resolução no meio (novo SPS) reinicia o decodificador **sem piscar** (o preview segura o último quadro — parte do preview é F3-T09).
- MFT: `IMFTransform` síncrono (decoder H.264 via `MFCreateSyncDecoderMFT`/attribute de D3D11 para hardware). Dependência: crate `windows` — **conferir os feature names no fonte do registry** (`%USERPROFILE%\.cargo\registry\src\*\<windows>-*\src`) antes de adicionar; não invente features.
- Fallback forçado: env **`LOCALCAMERA_FORCE_SW_DECODE=1`** (usa em todos os testes; a GPU real é coberta em IT-3.04).
- Saída: NV12 (o `compose` da F3-T08 consome).
- Fila: capacidade ~10 quadros; consumidor lento → **descartar o mais antigo** (preferir descarte de não-chaves; documentar a regra no código).
- Fixtures (já geradas em `fixtures/`, fora do Git): `hd30.h264` (1920×1080, 300 AUs), `no-idr-start.h264`, `corrupt.h264`, `sps-change.h264`.
- **MFT é o cartão de maior risco da fase** (instabilidade por driver). Regra: 2 falhas no mesmo ponto → parar, registrar em `PROGRESS.md` (Bloqueios) e pedir decisão (contingência do plano: FFmpeg dinamicamente ligado — só com ADR/decisão do usuário).

## Passos
1. `queue.rs`: `FrameQueue` (capacidade fixa, `push` descarta o mais antigo e conta descartes; unidade, testável).
2. `decoder.rs`: `H264Decoder::new(prefer_hw: bool) -> Result<Self, DecodeError>` (hw MFT → em falha, sw; env força sw); `send(&[u8] annexb_au, keyframe: bool) -> Result<Option<DecodedFrame { data: Vec<u8> /* NV12 */, width, height, pts_us, keyframe }>>`; `restart()` (novo SPS/PPS); eventos: `RequestKeyframe` (quando erro exige). Baixa latência: buffers mínimos, sem enfileirar no MFT.
3. Integração com a sessão: task tokio que consome os quadros `VIDEO` da sessão (canal do `lc-server` — conferir em `sessions.rs`; **se o canal não existir**, expor o mínimo necessário no `lc-server` com teste direcionado e registrar em Observações) e alimenta o decodificador; `STREAM_CONFIG` configura (resolução/`rotationHint`); `REQUEST_KEYFRAME` enviado à sessão quando o decodificador pede.
4. Testes com fixtures (sempre **forçando software** em CI — GPU não é determinística em CI).
